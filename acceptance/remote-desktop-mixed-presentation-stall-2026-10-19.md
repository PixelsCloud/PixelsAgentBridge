  随后约 1.9 秒恢复首帧，新会话只查看，但已从硬解切为软件解码。
- 本轮没有执行失败长测的“视频关闭后旧业务仍可用”步骤，不能借用短测补算通过。

  Wake Time 为 `23:40:11.7162425Z`。呈现异常比 Sleep Time 早约 24 秒；
  尚无直接显示电源状态证据，不能据此唯一认定异常原因。
- Linux 原服务、会话、显示布局已恢复；临时服务、媒体进程、测试输入设备和

## 代码定位与后续修正范围

Windows 原生呈现把尚未观察到的 present ID 保存为统计队列；旧实现达到三个
ID 时等待统计推进，超过两秒抛异常。统计记录不持有帧资源，实际 GPU 排队已有
swapchain latency handle 限制。因而统计缺失可以阻塞下一帧，最终触发整条会话
恢复及软件解码回退。这是代码中明确存在的依赖，原始统计停滞的外部触发仍未确定。

候选改为仅保留最近三个统计 ID，丢弃未确认的旧 ID，不增加显示帧数；保留真实
GPU 等待、提交、设备错误检查。关闭时等待统计最多两秒，未确认的 ID 不计数。
不会用提交次数替代实际显示 FPS。候选的构建与回归结果另行记录；原长测不改判。

微软说明 `GetFrameStatistics` 在部分多屏、其他全屏应用等场景下不可靠，硬件
翻转队列也可能使更新延迟；这些资料支持将统计和实际提交限流区分，但不能替代
本次故障复现：[API 文档](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/nf-dxgi-idxgiswapchain-getframestatistics)。

普通隐藏/恢复的独立窗口对照未复现该异常。首次关屏脚本使用广播消息，受到多个
窗口超时影响，最后显示计数为 9、颜色检查最大误差 4；显示数断言失败，不能算作
关屏恢复通过，屏幕已恢复。保留这一脚本失败，不将其归为产品呈现统计停滞。

后续带电源通知的对照也未通过：150 帧 GPU 颜色检查最大误差 4，但显示计数为
0。进一步检查确认本机 Windows 会话已锁定（WTS session 2、lock flag 0，
`OpenInputDesktop` 拒绝访问）。关屏触发了本机自动锁屏；不能把这种状态下的
画面计数当作解码或修正候选的性能结论。没有修改系统锁屏/电源配置，已请求用户
解锁。原生窗口回归新增前置检查，在锁屏状态直接给出明确失败，尚待解锁后重跑。
