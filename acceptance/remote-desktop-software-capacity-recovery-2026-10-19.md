## 问题与处理范围

原代码在 256×144、完整质量、逐像素生成随机 BGRA 的第一个公开帧稳定返回 OpenH264 native error 3。
该错误与先前[预算短测](remote-desktop-adaptive-bitrate-2026-10-19.md)保留的失败一致。
诊断时私有初始化帧以 QP 26 编码成功，切至既定 QP 14 后失败；内部返回 1，再被映射为公开错误 3。

核对固定依赖 openh264 0.9.8 / openh264-sys2 0.9.9 的 `welsEncoderExt.cpp`、
`nal_encap.cpp` 和编码配置：native error 3 同时涵盖真实分配失败与码流缓冲容量错误。
其中 NAL 封装会按原始负载的额外转义空间检查容量，失败也走此错误；失败后原生编码器被反初始化。
因此不能把每一个错误 3 都解释为系统内存不足，也不能在同一个已失效的原生编码器上直接重试。
本轮有界切片消除了所测输入的失败，未对所有可能的错误 3 声称同一根因。

最终处理为：

- 保持正常软件帧的既有质量、切片和预算策略。原 GPU 直编码及原采集转换路径不变。
- 仅首次遇到原生错误 3 时，用现有依赖支持的 8 KiB 大小限制切片重建软件编码器，重新编码当前保留的同一帧。
- 重建保留当前预算、转换平面和尺寸，第一帧携带独立解码需要的配置与 IDR；不跳过当前帧、不丢弃已经输出的压缩参考帧。
- 同一 `SoftwareEncoder` 生命周期最多切换一次。已在有界模式中再失败则直接返回错误，不无限分配/重试；后续预算变化保留这一模式。
- 不修改视频协议、分辨率、generation、屏幕坐标、认证或设备使用限制。

## 定向验证

Windows 执行 `cargo test --locked -j 2 -p pab-desktop-media --lib software::tests:: -- --nocapture --test-threads=1`。
最终 **15 通过、0 失败、1 个既有手动性能基准忽略**，测试执行 3.41 秒。
编译使用 Cargo 2 作业、嵌套原生构建 1、进程亲和性最多 10 核；启动前未观察到其他编译。
最终提交前仅整理新增代码的注释和格式，没有再次运行同条件测试。

| 范围 | 本轮观察 |
| --- | --- |

| NV12 已有帧后恢复 | 先公开一个普通帧，再在同一编码器中输入复杂 NV12，三阶段共 13 个公开帧连续解码；实际触发有界模式，没有返回旧画面 |

## 保留的失败与未采用方案

首次负向回归确实失败，退出 101；诊断轮保留原错误与详细 OpenH264 输出。
曾尝试对所有软件帧启用有界切片：复杂帧通过，但既有 64×48 渐变颜色检查得到
红通道 17.3375、目标 20，误差超过原阈值 2。因此未采用全局切片变更，也未放宽颜色断言。
随后限定为原生错误后的单次后备，原颜色与码量回归均通过。对应失败日志完整保留，未覆盖成成功。
