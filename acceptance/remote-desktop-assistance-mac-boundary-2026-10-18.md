## Windows：真实观看中的账号代次变化

构建当前 Desktop 前端及完整 Windows Desktop，通过，Cargo 使用 4 jobs。
另一会话后续有 2 jobs 构建，观察到的合计额度为 6。没有修改本机安装版。

采用独立配置目录，复制既有登录状态及 90 的设备凭据。没有调用服务器注销、
删除共享系统凭据或在安装版账号目录写入。测试原子替换独立目录内的账号状态：
已登录 → 本地未登录 → 同一用户的新 revision；**不等同于真实切换另一用户或服务地址**。

实际链路结果：

- MCP 请求显示协助提示；用户操作打开正式独立窗口，90 的 1920×1080 首帧进入
  viewing，实际解码报告为 D3D11，默认只查看。
- 第二个 MCP 会话不能读取第一个会话的协助请求。
- 本地未登录后提示消失；旧 MCP 请求不可访问，存储状态变为 cancelled /
  requester_unavailable；媒体子进程退出。上述观察约 2.26 秒完成。
- 恢复新 revision 后，旧 ID 的显示确认、取消、打开操作全部被拒绝。
- 新请求进入新窗口、新视频 session，重新实际显示画面且保持只查看。

旧窗口在采样时已拒绝操作，但当时缓存的界面文字仍显示 Connected；这份早期
快照不证明最终断开提示正确，后续需补充终态 UI 观察。没有在本轮发送远端键鼠。

测试收尾未完整通过：进程退出后的第一次目录清理遇到 `WinError 32`，随后两次
PowerShell 删除请求被自动审批以 `blocked by policy` 拒绝，未提供具体原因。
未改用其他方式绕过拒绝，剩余私有文件位于被 Git 忽略且 ACL 受限的目录：
`.build/remote-desktop/assistance-boundary-361931a68563/data`。
记录保持 `passed: false`，进程命令 exit 1；不能将功能步骤通过写作整轮通过。
后续只读复查没有该目录中的 Desktop/MCP 进程。原账号文件哈希比对在进程内执行，
但最终报告因清理异常未落盘，因此不把该比对列为已保存的独立证据。

90 原 Executor 已恢复 Running，输入释放标志为 0，测试进程为 0；随后移除五个
测试计划任务和远端 stage。服务临时切换始终有有界恢复任务；没有替换安装文件。

## Apple：固定 App 的权限和实际光标源

用户确认解锁后，单屏为 1920×1080 / scale 1。测试只控制自有光标窗口，没有
锁屏、注销或修改系统权限。原已授权测试 App 路径保持为：
`/private/tmp/pab-mac-media-99f879354739/Pixels Remote Desktop Test.app`。

将已编译候选代码更新到这个固定测试包，保留 bundle identifier 和签名身份，
先备份旧包，没有替换 `/Applications` 安装版。签名后 SHA-256 为
`60c8a5f5bfa30ed5fb919b5be950cf6760486463d4b2ee2adf9f19f47767c102`。
LaunchServices 启动 `--macos-check`，屏幕录制和辅助功能均为 true，检测到一块屏幕。

真实光标检查通过的阶段：

- 箭头：28×40，热点 (5,5)，形状负载 4480 字节。
- 自定义光标：9×7，热点 (3,2)，形状负载 252 字节。
- 横向移动 20 个桌面单位、移回：位置正确，形状负载为 0。
- 隐藏、重新显示：可见性正确，不重复发送未改变的形状。
- 恢复箭头：新 image_id，恢复原尺寸和热点。

裸 worker 和固定 App 的 LaunchServices 路径分别取得这七阶段证据。App 路径
通过测试 FIFO 转接；记录中的 worker_sha256 是转接脚本哈希，实际 App 哈希
单独记录，不能混淆。普通光标测试未请求视频帧。

随后固定 App 同时运行实际视频采集和独立光标源，`desktop-separate-cursor`
模式下取得五帧 H.264（首帧关键帧），同时验证箭头、自定义、隐藏、显示、恢复。
只检查协议和光标元数据，不保存桌面图像。正常停止后各 worker exit 0。
这不证明视频像素中绝无重复光标、不测实际显示 FPS，也不替代正式远程窗口验收。

## 保留的失败与修正

首次裸 worker 收到箭头后等待自定义形状超时。独立探针、相同源码原生对照、
裸 worker 复测及固定 App 复测随后通过；未改变产品代码，首轮原因未确定，
不能记为已修复产品缺陷。

从 Python 直接启动裸 worker，以及直接启动 App 内二进制，屏幕录制均被拒绝。
LaunchServices 启动的同一固定 App 权限检查和实际采集通过；测试遵循既有 App
启动身份，没有要求用户重复授权。`open` 直接引用 `/dev/stdin` 的尝试失败，
改用已有验收所用的私有 FIFO 方式。

FIFO 转接器自身有两项问题：

1. 默认 kqueue 的边沿触发未排空大视频包，读到帧头后超时；改为水平触发的
   SelectSelector 后，148982 字节的首帧及后续四帧完整读出。此修改仅在测试驱动。
2. `native_cursor_check` 经转接器返回成功，但销毁视频时杀掉的是转接器，App
   的 FIFO 描述符仍然存在，留下八个媒体进程；一次失败视频轮次另留一个。
   因此撤销“生命周期已通过”的解释，该转接方式不能验收父进程取消。
   后续按已观察的 PID、完整可执行路径和精确参数逐个核验并终止这些测试进程。

最终独立复查：Apple 本轮媒体/fixture 进程为 0，九个残留 FIFO 临时目录已清理，
原服务仍加载；固定 App 和签名备份保留供后续测试。下一步需在正式 session helper
的匿名管道链路验证取消/回收，再验证 Windows→Mac 正式窗口的光标、输入和登录。

本轮没有运行安装包、COS 发布、跨平台矩阵或长时稳定性测试。
