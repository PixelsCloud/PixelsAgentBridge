# 编码码率反馈、稳定恢复与降档状态

日期：2026-10-19。基于 `80c9dba` 的独立远程桌面 worktree。
本轮完成码率目标与既有采集节奏的反馈连接，保留原屏幕和编码尺寸。
06.1 仍为部分完成，不把本机短测替代跨平台弱网验收。

## 实现与兼容边界

- 继续使用既有可靠传输、最多四帧在途和五秒积压期限；仅使用发送端单调时钟。
  首次显示的解码器启动等待不降档，持续消费压力才触发编码器预算。
- 原始质量 → 3 / 1.5 / 0.75 / 0.35 / 0.15 Mbps 目标，降档间隔至少两秒；
  连续无压力十秒后逐档恢复。零值恢复原有完整质量，码率是目标而非硬性上限。
- Windows 更新 NVENC rate control，macOS 更新 VideoToolbox AverageBitRate。
  不能在线更新的硬编保留原直接纹理/IOSurface 路径，返回不支持；
  不为了改码率改用 CPU 回读。原有编码失败的软件后备仍保留已应用的预算。
- OpenH264 从固定质量切换到码率模式时仅重建编码器，保留转换平面与采集资源；
  下一帧带 SPS/PPS 和 IDR，保持帧号顺序。初次尝试仅更新运行参数虽返回成功，
  实测码量未下降，因此未采用。始终禁用编码器跳帧，不丢弃已编码的参考帧。
- 新增可选的独立质量查询流，沿用原连接/账号/观看者和 generation 检查。
  查询不返回视频额度、不续控制租约；不支持诊断的旧端不影响原视频。
  原有 v2 Open、控制回复及视频帧格式保持不变。
- Desktop 增加独立降档事件，旧会话/旧 generation 状态不覆盖新画面，
  不借质量事件清除正在等待的工具栏操作。显示的是编码目标或采集上限，
  明确不将其标成实测显示 FPS。修正了纳秒取整会将正常 15 FPS 误显示成降档的边界。
- 本轮没有改变编码尺寸、屏幕原点/旋转/DPI、归一化输入坐标、鉴权或设备数量限制。

## Windows 原生 1080p 短测

仅生成合成四象限画面，不保存真实桌面或压缩视频，不注入输入。
每条路径提交并实际确认显示 90 帧，前 15 帧预热；中途设置 1.5 Mbps，再恢复默认质量。
四像素颜色验证有诊断回读；下表的回读次数只描述采集/编码路径。

使用 `profile.dev.package.pab-desktop-media.opt-level=2` 的优化媒体构建，
Cargo 仍标记 dev profile；这不是三平台正式 release 安装包。

两条路径都实际确认了预算命令、连续帧顺序和解码输出；未证明实际跨网络限速后的自动降档。

保留失败结果：

- 首轮硬编显示 90 帧、14.46 FPS，但窗口重画增加四次像素检查，原探针要求恰好 360
  次而失败。原生代码已明确重画不计新视频帧；探针改为允许额外颜色检查，并要求
  预算循环的 90 帧全部显示，未修改产品的呈现计数。
- 未优化媒体的调试构建软件路径只有 **7.76 FPS**，不能记成性能通过。
  优化构建的转换/编码均值从 103.88 ms 降为 42.47 ms；最终包仍必须单独测量。
- 额外的 256×144 全屏逐像素随机噪声压力输入，在完整质量的首帧阶段曾返回
  OpenH264 native error 3，尚未定位。本轮色块通过不覆盖该高熵输入边界。
