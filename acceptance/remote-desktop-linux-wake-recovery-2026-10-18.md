# Linux 锁屏过渡期间的显示唤醒恢复

日期：2026-10-18。基线 `e150ebe`，对应 W3/W5。脱敏采样、源码/产物/原始记录哈希见 [验收数据](remote-desktop-linux-wake-recovery-2026-10-18.json)。本轮不关闭整个 W5 或密码登录要求，清单仍为 9/53 完整关闭。

## 问题与改动

在 Ubuntu 22.04 / GNOME 42.9 / VMware Wayland 单屏 1314×704 上，检测到 `LockedHint=yes` 后立即启动正式内嵌 worker，旧版本再次出现 `Display did not wake`。同轮普通桌面三次通过；锁屏后显示电源保持 3，直到原等待时限结束。没有通过给测试添加两秒等待来规避。

保留原 supervised broker 首次唤醒。等待期间若显示仍关闭，每隔至少 750ms 尝试重新唤醒，最多两次；先关闭旧 exporter socket，再通过同一受会话约束的 broker 连接。重发输入后若显示仍关闭，由用户会话调用 Mutter `PowerSaveMode=0`，继续读取实际电源状态后才能开始采集。原有旧画面、布局、锁屏状态校验保持；失败仍退出当前代次。

该接口是显示的即时电源状态，不写节能或自动锁屏配置；不写未知/不支持的 -1 状态。参见 [Mutter 42.9 DisplayConfig 接口](https://github.com/GNOME/mutter/blob/42.9/data/dbus-interfaces/org.gnome.Mutter.DisplayConfig.xml)。GNOME 的锁屏活动监听与动画分阶段执行，见 [ScreenShield 实现](https://github.com/GNOME/gnome-shell/blob/42.9/js/ui/screenShield.js)；本轮没有跟踪其内部事件，不能把特定内部竞争路径宣称为已经证明的根因。

等待保留三秒观察期限；每次 broker ACK 和 D-Bus 调用各有既有独立超时，因此这不是整个启动过程三秒的硬上限。父管道退出仍取消等待，重试不发送用户点击、文本或密码。

## 验证

- Linux 完整 Release Desktop 构建通过：1 分 28 秒；媒体库 **25 项**通过。最终 SHA-256 为 `6294fb4bfd985a16248eb5ed2da28b1d6d4d2c93a065ca7c9072feb95164754d`。Cargo 4 jobs、嵌套 native 1；另一个独立原生测试编译为 1 job，本轮编译并发不超过 5。
- 新原生 `native_linux_wake.cpp` 在隔离 D-Bus 上 **11 项** ASan/UBSan 检查通过：已点亮/未知状态不写电源，三种休眠状态点亮，写入拒绝传播，一次/二次重试，持续关闭超时，broker 错误和父管道取消。LeakSanitizer 未开启；不是实际桌面或长期泄漏测试。
- 输入重试版本在不加等待的三轮立即锁屏检查中通过，但未触发重试日志，不能据此证明分支有效。
- 为触发分支，测试在锁屏后的首次点亮时仅一次临时设置电源为关闭。输入重试版本两次重试仍超时；最终版本一次重试后恢复点亮，从注入结束到首次采样为 0 约 **1.193 秒**。这是定向电源故障，不等同于精确重现 GNOME 内部竞态。
- 最终同一测试包含普通桌面三次和锁屏三次：每次先取得独立光标，再解码五帧，检查坏光标客户端隔离、重连及停止。普通桌面 fd 低值 33→33，锁屏 13→13；停止约 35～66ms，broker 无错误、socket 回收。
- 原服务 active，原程序/配置/服务文件哈希保持，原会话恢复解锁。临时进程、目录及转移文件清理。测试解锁使用已授权的 `loginctl unlock-session`，不是系统密码登录验收。

## 正式独立窗口

Windows 隔离 Desktop（SHA `129550c8a89a0375e251274682edc7ca3a445acedf251c3e34b01cf5de5e95a9`）连接最终 Linux 产物。按住 Ctrl 后锁屏，同一父窗口约 **2.695 秒**自动恢复锁屏画面；解锁后约 **2.644 秒**恢复动态夹具。两次均回到仅查看，实际解码报告为 `d3d11_hardware`；没有手动重连。锁屏截图可见系统时间及光标，解锁后生成区域继续变化。

按键事件计数不是跨焦点释放的充分证据：锁屏获取焦点后，原窗口不一定收到 release 事件。夹具保留历史事件计数，另外读取 [GDK 当前修饰键状态](https://docs.gtk.org/gdk3/method.Keymap.get_modifier_state.html)。最终检查在焦点有效时确认锁屏前 Ctrl 为 true，解锁后为 false；没有把历史 `ctrl_held` 强制清零来使检查通过。

正常关闭后无自有媒体进程；原服务、配置和会话恢复，七个本地私有文件及远端临时资源清理。最终驱动 exit 0。正式窗口记录 `formal-linux-login-2c107b7248bc/product-wake-recovery-result.json`。

## 保留失败

- `b8376afc6d`：旧产物立即锁屏的真实唤醒失败，保留完整电源采样。
- `eaeb29474c`：输入重试版本首次通过，但没有实际触发重试。
- `c8b3c25760`：恢复画面后 fd 单次快照 13→15 断言失败。独立光标线程正在周期性接收一对 DMA fd；修正夹具为前后各 30 个样本、7ms 间隔的低值比较，并保存全部样本。后续实际样本证实 13/15 的短暂波动；这不替代长期泄漏检查。
- `c91ac47a18`、`a5107e8c6f`、`ce93771e86`：改进计数后的自然立即锁屏通过，仍未触发重试。
- `e710e1c256`：定向再次关屏故障下，只有输入重试仍失败；原服务和会话已恢复，后续只读检查电源为 0。
- `9c8cf6c9e5`：最终实现的定向故障、视频/光标和清理全部通过。
- 原生测试最初两次取消断言失败：GTestDBus 的 watcher 子进程继承了测试管道写端。改为先启动隔离总线，再创建测试管道，产品未为此更改。最终 11 项通过；GLib 测试总线退出时的环境变量 debug 提示保留在日志。
- 正式窗口 `e7d47567deab`：画面恢复通过，但旧夹具把历史 Ctrl 事件标志当作实际按键状态，验收失败。新增当前修饰键观测后完整重跑通过；没有把这轮改记为成功。
