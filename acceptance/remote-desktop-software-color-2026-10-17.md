# 软件编码的渐变后色差回归

2026-10-17，基线 `7544347`。继续追踪 Linux 注销登录后留下的稳定色偏，
不修改原有 RGB 误差门槛。候选修复显式设置 OpenH264 的层 QP；不能用局部
通过关闭 W3/W5/W7/W8。
完整二进制哈希、原始事件、反例日志和清理结果见
[机器可读记录](remote-desktop-software-color-2026-10-17.json)。

## 根因与实现

从正式 Windows 窗口复现：Linux 测试窗口重开并稳定后，部分背景采样点从
`[21,81,74]` 变成 `[19,81,72]`，持续到 35 秒观察结束。原始 Cairo 颜色为
`[20,81,74]`。直接读取生产 PipeWire 采集路径的 270 个点，全部与 Cairo 一致；
额外诊断排除了光标覆盖，未把光标颜色当成色彩转换错误。

同一生成画面经过空间渐变后，原编码器保留了不同的色度值。查看本地固定依赖
`openh264-sys2 0.9.9` 的 `ratectl.cpp::WelsRcPictureInitDisable`，确认
`RC_OFF_MODE` 且关闭 adaptive quantization 时读取 `iDLayerQp`，不采用
`iMinQp/iMaxQp` 限制。包装器 `.qp(...)` 只设置后两者，上游默认层 QP 是 26
（`wels_const.h::SVC_QUALITY_BASE_QP`）。因此只收紧 `.qp(20,20)` 没有解决问题。

生产软件编码器在尺寸惰性初始化后显式设置 `sSpatialLayers[0].iDLayerQp`，
单切片小尺寸也设置；保留大图的四切片并行和首个公开帧为 IDR 的约束。
硬件直接编码分支、认证、可靠传输及输入语义不变。

## 保留的反例

- 新回归使用 64×48 与 512×288 的空间棋盘渐变，再显示纯色；以独立 BT.709
  反算验证原 RGB 每通道 ±2/255。原生产代码在 512×288 失败，结果约为
  `[17.34,82.24,69.65]`。初稿错误地要求 YUV 无损相等，已改为原 RGB 标准，
  没有扩大 RGB 容差。
- QP 24 在 64×48 失败，红通道约 17.34。QP 20 初次通过六项软件测试和
  Windows 十二项媒体测试，但完整 Linux 测试随后失败；同一二进制单独运行
  该回归十次，五次成功、五次失败。单线程运行全部 Rust 测试仍失败，说明
  不能归因于测试框架并行。
- 固定切片边界的 QP 20 十次全部失败；将编码器改为单线程的隔离对照十次通过。
  保留并行的 QP 14 和 QP 8 各十次通过。多切片分区影响预测/量化后的颜色，
  不将调度导致的某次通过视为稳定质量。候选采用 QP 14。
- 正式测试另遇到 1297×752 采集启动 EOF。生产 `Capture::start` 明确拒绝奇数
  尺寸；这是尚未修复的产品限制，不能靠临时设置测试分辨率关闭。

## 成本与边界

2 vCPU 的独立 1080p 四色块编解码对照中，原编码约 29 ms/帧，QP 20 约
41 ms/帧，编解码合计约 21.7 FPS；空间渐变码流约从 741 KB 增至 1001 KB。
这些是 QP 20 的诊断数据，不是 QP 14 的性能或网络帧率证据。软件质量提高会
增加 CPU 和码流成本，后续候选必须重新测量，不从硬件路径的成绩推断。

所有真实测试使用临时服务覆盖和独立回滚计时器，未替换安装文件。已核对原
Executor、服务单元、TOML 哈希、原图形会话、原显示布局，清理测试进程、输入
设备、runtime 目录及 Windows 私有 profile。只有生成颜色/帧编号与聚合诊断
进入验收记录，不发布登录凭据或用户桌面原图。

本次候选没有替代全部平台最终验收：仍需 Mac 构建与软件回归、原注销登录场景
重验、Windows 软件性能复验、奇数尺寸，以及主任务中的多屏、平台矩阵、长稳、
主线集成和发布。用户真实画面比对、更多颜色与高复杂度内容也不能从单色测试推断。
