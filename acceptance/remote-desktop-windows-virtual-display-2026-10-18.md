## 实测

在 90 session 2 的 user 上下文执行十秒测试：

1. 原主屏 DISPLAY1 保持 (0,0)、1920×1080、主屏标记。
2. 添加索引 0，得到 DISPLAY15，位置 (1920,0)、1920×1080、非主屏。
3. 五次两秒间隔采样均观察到两块活动输出，原主屏属性不变。
4. 请求移除索引 0，三秒后仅剩原主屏；活动拓扑与开始时逐项相同。
5. 临时二进制删除，Pixels 安装服务的状态、命令行与 PID 前后相同。

随后以实际 Desktop 内嵌媒体程序 `--media-worker inventory` 做二十秒复测：开始
一屏，四次采样获得双屏，移除期间一次采样回到一屏，结束状态与开始完全一致。
主屏 ID `0:81493:\\.\DISPLAY1` 在全过程保持，副屏 ID
`0:81493:\\.\DISPLAY15`、位置 (1920,0)，无重复 ID。实际 Desktop SHA-256：
`2f328f6ad2eabeeb7373e4d84607216c38960ddbf9da91710ced0ca98d05d5e0`。
两份临时二进制均删除，原安装服务保持。此结果证明原生枚举可识别该双输出及移除，
仍不代表正在观看的窗口已自动刷新或恢复。

上述检查未采屏、发送键鼠或测试 viewer 切屏，不能宣称多屏功能验收通过。
机器已有虚拟显示器驱动，可继续做真实 Windows 输出路径上的切屏和热插拔验证，
无需等待四块物理屏全部可交互。后续仍需负原点、DPI、旋转与移除后恢复。

编译每次固定一核；MSVC C++17、`/EHsc /MT`，通过 `/I` 指向上述私有头文件目录，
链接 user32.lib（头文件声明额外 SetupAPI/CfgMgr32 依赖）。执行前需确认当前
活动桌面及原始拓扑；结束后对比拓扑并确认进程退出，再删除本次精确暂存路径。
