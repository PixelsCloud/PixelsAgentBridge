# E3 原生用户二进制传输后端

## 本次实现

- 从现有上传/下载实现抽出 `TransferEngine`。service 适配器仍使用同一 QUIC 流和 TaskStore；校验、临时文件、哈希、覆盖/硬链接发布及传输记录沿用原实现。
- 文件 IO、流式网络适配和记录保存分别通过 `TransferStream` / `TransferRecorder` / 已有 FileLocks 协调。复用 Tokio、serde、SHA-256 和已有原生 user-worker，不增加库或常驻进程。
- 内部 transfer worker 用已核对 PID/UID/SID 的 IPC。控制消息保持有界，文件内容使用独立二进制帧，通道容量 8，每个数据块有背压；不把整个文件转成 JSON 或一次读进内存。
- 用户进程负责打开、写入、临时文件、哈希和最终发布；父进程负责数据库及跨用户共享路径锁。记录事件不携带可改写的 request_id，父端预先绑定原任务。
- 发布前等待父端持久化确认；最终回执在工作进程退出并完成清理后再转发。父任务取消时先回收子进程，再释放父端锁。
- 用户临时文件名包含实际执行身份的哈希，避免不同身份与 service 直接复用同名续传文件；原服务传输的文件名保持兼容。
- 通用传输引擎独立拒绝空、过大和超过声明长度的数据块，不能依赖某一种适配器替它验证。

## 验证

三平台 `cargo test --locked -p pab-executor --lib transfer`：各 9 项通过，原生身份 fixture 默认忽略后另行显式运行。

既有实际 QUIC 测试继续覆盖丢失回执、上传中断、并发路径冲突、空文件、分帧边界、源内容/校验和改变及传输记录重开。
新增协调测试覆盖发布确认之前断开时原文件不变、实际发布后丢失完成确认时仍可核对、锁保持至工作结束、适配器异常分块以及下载从 64 KiB 偏移继续且保存完整哈希。

`native_user_transfer_worker_acceptance` 在实际用户进程中执行：约 192 KiB 二进制上传，64 KiB 后断开，再以同一身份续传；下载从 64 KiB 开始，核对剩余字节和完整哈希；中文路径、文件所有者、空文件、共享路径锁、错误内容不发布、初始取消、服务私有目录读写拒绝。

| 平台 | 结果与任务 |
|---|---|
| Windows90 SYSTEM → WTS1 Administrator / WTS2 普通用户 | 两轮通过；`5aa5ab8e-4062-4c5c-9b01-3e30bcb39610`，退出 0，末尾目录/工作进程均为 0 |
| macOS root → UID501 | 通过；`ff975442-7ab7-45ab-905a-5021492dede5`，退出 0；清理 `cc9395c1-ce6b-4d99-9233-02406e721f11` 确认均为 0 |

Windows workspace tests 编译检查通过，三平台 Executor 构建通过。当前用户传输父端入口尚未接入公开 dispatch，因此普通库构建仍有该入口及其 OwnedWorker 的未使用警告；测试构建实际调用它，后续公开接入将消除警告。

## 明确未完成

此阶段原生测试使用流适配器驱动真实用户工作进程，服务默认传输经过 QUIC；尚未证明用户传输的完整 QUIC/Bridge/MCP 公开链路。

下一增量必须一起完成：

1. 公开 execution 参数、能力版本、原子身份记录、参数指纹与重复 ID 规则。
2. 同一传输恢复时固定原身份；将 TaskStore 现有的服务权限文件核对分流到原用户只读核对。当前原生测试成功不能代表这一恢复路径已完成。
3. Bridge 异步队列、实际身份展示、取消与观察及公开工具测试；相同 ID 查原结果，显式续传尝试保持原身份和内容约束。
4. E6 运行中取消/进程崩溃/重启/两 MCP 并发、长时间哈希的观察边界、路径替换等完整矩阵。

版本仍为 1.2.26；没有替换正式服务、增加版本或打安装包。正式宿主验收仍待 E8。
