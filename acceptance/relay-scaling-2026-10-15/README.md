## 90 公网部署

- 已核实设备 428358431，系统为 Windows Server 2022；原 `PixelsAgentBridgeExecutor` 未覆盖安装、配置或身份。
- Server 使用公网 TCP 4800，原生 Windows Relay 使用 TCP 4801；独立目录 `C:\PixelsRelayScalingTest`，独立服务 `PixelsRelayScaling90ServerTest`、`PixelsRelayScaling90RelayTest`。
- Linux Relay 在另一台测试主机原生运行。其公网 4802 无法从外部访问，本轮通过 90 的临时 TCP 4802 入口和专属原生 OpenSSH 隧道发布；TLS 在 Linux Relay 终止，显式校验测试 CA。
- PostgreSQL 位于本机专属隔离容器，仅绑定回环地址；90 通过已有 Pixels P2P 通道中的 SSH 转发连接，不公开数据库端口。公网 Relay 数据、控制 WSS 与数据库隧道分开。
- 外部网络对两个入口完成 HTTPS 和双向真实转发探针；Linux Relay 控制 WSS 直接连接 90 公网 4800。
- 公网两组端点分别经过两个节点并发传输共 64 MiB，摘要一致，耗时 **114.415 秒**，符合账号共享 10 Mbps 上界；公网链路未达到账号速率上限。
- 公网连续切换 **20 次**，四个端点身份与内容校验全部通过；端点观察到的恢复耗时约 **1.4—7.9 秒**，包含管理调用最长 **8.05 秒**。切换前后 RSS 为 35,794,944 / 38,793,216 字节，句柄 306 / 310，线程 28 / 29。
- 90 原生 Relay 的 30 秒维护、逐节点更新流程、摘要核验和恢复真实转发通过；本轮正常更新复用了同一 Relay 程序摘要并验证新 boot，坏程序导致不同摘要的失败及原版本恢复另由 Windows 隔离回滚测试覆盖。
- 90 原生 Server 重启后，Windows/Linux Relay 控制重连、健康恢复和双向转发探针通过。测试端点正常关闭。
- 最终用原生安装助手移除两个 Windows 测试服务；额外查询确认服务已删除、4800—4804 测试监听关闭，临时防火墙规则、计划任务、测试管理员和 SSH 密钥已清理，原 Executor 仍运行。Linux 测试服务已停用，专属数据库容器已删除。初次自动清理被测试脚本的 SSH 连接替换逻辑阻断，已修正并单独完成状态核对；未把初次失败回执当成清理成功。

两个测试入口都经过 90，因此没有覆盖“90 整机离线、另一台主机独立公网入口仍可用”的情形。生产每个 Relay 应提供独立稳定入口。

## 验收中修复的问题

- 没有结尾斜杠的 TOML URL 曾使控制器误判健康节点；现在先规范化再比较。
- Server/Relay 墙钟偏差曾拒绝刚收到的策略；集群改用服务端时间锚和单调时间，旧模式保持原行为。
- 目录读取曾争用全局写锁；改为一个 SQL 的一致 MVCC 快照，仅过期状态变化进行写入。
- Windows CIM/WMI 曾使部署指令超时；助手改为直接访问 SCM，并以有限权限查询真实运行映像。
- 升级器中断后恢复指定的原程序 SHA-256，不能靠再次执行回滚来猜当前版本。
