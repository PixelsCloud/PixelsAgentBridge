# Windows 原生输入开发与验收

工作分支：`feat/remote-desktop-v1`。本轮在独立 worktree 开发，不覆盖本机安装版，
不修改主工作区其他会话的代码。编译最多 8 jobs，另一会话运行 2 jobs 时合计不超过
10；独立 C++ 诊断仅使用 1 core、1 个编译进程。

## 实现

- 独立远程桌面窗口默认只查看，收到首帧后才允许启用操作；切屏、重新连接和
  修改 FPS 均重新要求启用操作。窗口失焦、失去鼠标捕获时发送释放。
- 原生子窗口采集鼠标、键盘、滚轮事件。根据视频有效区域计算坐标，排除黑边，
  拖拽出界时夹紧坐标；竖屏使用已旋转的可见区域，不再次旋转或乘 DPI。
- 视频 ACK 与输入事件使用不同本地管道；连续鼠标移动可合并，按键释放和模式
  切换确认不可丢弃。滚轮先定位，再发送滚动，避免丢失此前合并的鼠标位置。
- 输入使用现有设备认证、可靠控制通道和 generation；处理输入不取消待接收的视频
  半包，不占用旧截图、应用和窗口请求队列。
- 独立 SYSTEM 媒体 helper 覆盖 Default/Winlogon；旧窗口和应用 helper 保持原用户
  身份。OS 输入由单独子进程持有，关闭管道触发释放，监测进程退出以恢复崩溃时的
  按键。新输入必须等待旧进程退出和释放恢复。
- 每个 Windows 会话保存 259 字节运行时释放标记，仅包含仍需释放的键和鼠标按钮；
  不保存文本或输入历史。文件位于 helper 自身 LocalAppData 下的
  `PixelsAgentBridge/remote-input/session-N.releases`，独占打开。按下前持久化，
  OS 接受释放后清除；不能确认时保留标记。此文件是运行时数据，不是应用配置。

## 90 实机发现与修复

使用独立临时 Executor、SYSTEM media supervisor 和限时测试窗口，不替换安装文件。
提前注册恢复原服务的任务，测试控制器使用现有账号和已保存设备密码。

初轮实际点击、F24 按下/释放、Ctrl 按下、滚轮均被目标窗口观察到；停止操作时
发现 Ctrl 释放失败，不能将前面的 API ACK 计为完整输入验收。先通过已有输入
通路恢复按键，原服务按预定任务恢复。

问题是释放线程绑定的桌面句柄只申请了 READ/WRITEOBJECTS 等权限；绑定后
`SendInput` 被拒绝，持久化释放标记正确保留，新 helper 因此等待恢复而不继续输入。
改为按当前系统令牌申请 `MAXIMUM_ALLOWED`，不改变设备认证规则。独立恢复程序
已在 90 的交互会话中成功运行，待释放标记从 1 归零。

这与 Windows 的[桌面线程绑定规则](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setthreaddesktop)
一致：绑定后的操作受该句柄权限约束。参考了本地 RustDesk
`src/platform/windows.cc` 中选择输入桌面时包含写入权限的处理，未复制其实现。
