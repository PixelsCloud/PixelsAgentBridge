# 首轮远程桌面实验记录

日期：2026-10-16。分支 `feat/remote-desktop-v1`，独立 worktree。尚未接入生产 Cargo 工作区、网络协议或 Desktop 页面。

## 最新进展：Windows 硬解与原生显示闭环

新增独立 `loopback-probe.exe`：GPU 合成图 / DXGI 桌面 → 原纹理 NVENC H.264 → 内存码流 → Windows Media Foundation / D3D11 DXVA → NV12 解码纹理 → GPU 视频处理器 → BGRA flip swapchain。两台机器分别在本地执行整条链路，没有用网络发送视频，也没有更新已安装 Pixels。90 沿用现有 Administrator 用户上下文，未创建账号。

编码和解码尺寸均为 1920×1080；测试窗口客户区 960×540。每次提交后按 DXGI frame statistics 确认对应 present ID，确认后才处理下一帧。以下为最终版本单次 5 秒测试，未扣除首帧和结束 drain，帧数均满足编码 = 解码 = 已确认显示：

| 机器 / 场景 | 显示帧数 | 有效显示 FPS | 本地源帧到显示确认 P95 |
| --- | --- | --- | --- |
| 本机 RTX 3060，GPU 合成图，15 FPS 档 | 75 | 14.9738 | 16.6285 ms |
| 本机 RTX 3060，GPU 合成图，30 FPS 档 | 145 | 28.9526 | 17.7181 ms |
| 本机 RTX 3060，DXGI + 动态窗口，15 FPS 档 | 75 | 14.9595 | 17.1864 ms |
| 本机 RTX 3060，DXGI + 动态窗口，30 FPS 档 | 144 | 28.7270 | 49.6769 ms |
| 90 RTX 4090，GPU 合成图，30 FPS 档 | 150 | 29.9675 | 16.5594 ms |
| 90 RTX 4090，DXGI + 动态窗口，30 FPS 档 | 150 | 29.8992 | 17.0604 ms |

显示确认来自系统统计，延迟包含 GPU 完成等待、垂直同步、DWM 调度及约 1 ms 轮询粒度，不是光学屏幕延迟，也不是跨网络的端到端延迟。本机 30 FPS 动态桌面仍有约 50 ms 的尾延迟，后续网络测试需要继续观察，不能仅凭平均 FPS 宣称低延迟问题已全部解决。合成图逐帧变化；真实桌面测试不回读像素，因此不额外声称对每个采集帧都做了内容差异验证。

正确性单独运行 `--verify-pixels`：每帧四色象限在不同位置变化，读取四个输出像素，核对颜色和帧号。两台机器各验证 75 帧、300 个像素，本机最大 RGB 通道误差 3/255，90 为 2/255，低于 12/255 门限。早期错误使用 BT.601 时此检查失败；最终显式声明并按 BT.709 有限视频范围、全范围 RGB 显示后通过。正确性测试有少量像素回读，不计为无回读性能场景。

资源交接与复制边界：

- 编码器仍直接注册采集纹理；采集 lease 在编码完成后、解码/显示等待之前释放。
- 解码必须返回同一个 device 上的 NV12 `D3D11_BIND_DECODER` 纹理及具体数组槽位；CPU buffer 后备直接失败。
- 持有解码 sample 到 GPU 转换完成，避免解码器提前复用槽位；实际最大待解码帧数为 1，实验硬边界为 4。
- 1080p 解码纹理的对齐行按可见 aperture 裁剪，不能把 1088 行拉伸成 1080 行。
- 性能场景没有应用显式像素 CPU 回读或中间纹理复制；每帧有一次必要的 NV12→BGRA GPU 转换/缩放。驱动与 DWM 内部复制未知。

30 FPS 动态桌面场景，本机进程峰值工作集约 81.24 MiB、采样本地显存峰值约 99.90 MiB；90 分别约 80.91 MiB、103.18 MiB。进程 CPU 时间折算约占 0.0468 / 0.00934 个逻辑核心，属于 5 秒短测，未包含 DWM 和系统驱动全部开销，GPU 引擎利用率未采集。

验证脚本通过参数拒绝、禁止真实桌面像素回读/保存、关闭本脚本自己创建的查看窗口后进程清理。重建原编码探针后，15/30 FPS 合成码流分别通过 75/150 帧独立软件解码、逐帧哈希、无 B 帧和输出文件保护回归。构建使用单个编译任务、至多 10 核亲和性；发现 Android 会话在 `-j 10` 编译时等待其结束。

90 的短暂测试窗口已退出，上传的唯一临时 exe 已删除，清理命令退出码 0。未锁屏、重启、注入键鼠或改服务。验收汇总为 [remote-desktop-loopback-2026-10-16.json](../../acceptance/remote-desktop-loopback-2026-10-16.json)，仅包含测量数据，不含凭据、码流或图片；原始记录保存在忽略目录 `.build/remote-desktop/loopback/verify-e69b7cdf9cf2/report.json`、`90-loopback.json`，编码回归为 `.build/remote-desktop/nvenc/verify-ee4ac19b6c79/report.json`。

下一阶段接入现有可靠流和认证、单查看占用与屏幕 generation。产品独立窗口、多屏切换/旋转、输入、锁屏、Mac/Linux 媒体以及软件后备仍需开发，不能把本地媒体实验当作完整远控功能已完成。

## 后续进展：直接纹理编码

已同步主分支 `e22c45b`。此前查询限额故障已在独立修复中提交，四个客户端渠道已发布；控制服务尚未部署，不能将其认定为线上限额已解除。

新增独立 NVENC 编码实验，直接注册 D3D11 BGRA8 纹理，低延迟 H.264、目标码率 6 Mbps、无 B 帧或 lookahead，单帧等待编码完成后才释放采集资源。没有引入 FFmpeg 编译依赖，没有修改生产传输或安装程序。

| 场景 | 编码帧数 / 时长 | 编码吞吐 | 编码 P95 |
| --- | --- | --- | --- |
| 本机 RTX 3060，1080p GPU 合成图，15 FPS 档 | 75 / 约 5 秒 | 约 15 FPS | 初测 2.56 ms |
| 本机 RTX 3060，1080p GPU 合成图，30 FPS 档 | 150 / 约 5 秒 | 约 29.93 FPS | 初测 2.51 ms |
| 本机 RTX 3060，1080p DXGI + 动画测试窗口 | 150 / 5.023 秒 | 29.8626 FPS | 2.9974 ms |
| 90 RTX 4090，1080p GPU 合成图 | 150 / 5.002 秒 | 29.9906 FPS | 1.8884 ms |
| 90 RTX 4090，1080p DXGI + 动画测试窗口 | 150 / 5.010 秒 | 29.9416 FPS | 1.9460 ms |

本机合成码流经独立 FFmpeg 软件解码：75/150 个输出帧均可解码、逐帧哈希各不相同、无 B 帧。可重复验证脚本同时通过无效参数、禁止保存真实桌面、已存在输出文件不覆盖的检查。不能把此软件解码检查说成产品硬解码已完成，也不能把编码 FPS 当成接收端显示 FPS。

本机无测试动画时仍有正常桌面更新，取得约 15 FPS；90 静止桌面只有约 1.19 次更新/秒，因此单独加入 5 秒不激活的测试窗口。90 使用现有认证连接及既有 Administrator 用户执行上下文，未创建账号或更改服务；窗口自动关闭，两个上传的临时实验 exe 均已删除。没有锁屏、重启或注入键鼠输入。

实验代码没有像素 CPU 回读、`CopyResource` 或显式格式转换；硬件/驱动内部处理未知。压缩码流输出位于 CPU 内存，为下一步可靠传输准备；每帧注册/解除注册的 CPU 开销已计入编码耗时，资源缓存复用尚未优化。

原始证据位于 `.build/remote-desktop/nvenc/`：`verify-fec8394fee6a/report.json`、`verify-b47f3ac9d548/report.json`（最终代码含动画场景验证）、`dxgi-animated-30.json`、`90-native-user.json`、`90-animated.json`、`90-cleanup.json`。下一步完成硬解码纹理交接和原生显示，之后继续可靠流、单查看会话及屏幕 generation。

## RustDesk 媒体源码审查

参考版本见 `sources.toml`，不是运行性能结论：

- hwcodec `cpp/nv/nv_encode.cpp` 的 SDK 默认路径接收 GPU 纹理，但在 `encode()` 中仍执行 `CopyResource` 到编码器输入资源。开发用跨显卡分支另有 staging/Map，不能把它混入默认路径计数。
- `cpp/ffmpeg_vram/ffmpeg_vram_encode.cpp` 为 NVENC/AMF/QSV 选择 NV12 输入，调用 `BgraToNv12`。接口接收纹理不代表没有格式转换。
- `examples/pipeline_vram.rs` 固定 LUID、H265、无限循环，并把码流写入文件，不适合原样用于本项目验收。
- 下一步需在固定依赖基础上验证直接注册兼容采集纹理的编码路径、资源持有和同步；确有必要的 GPU 复制/转换必须单独计量。FFmpeg 开发库与 SDK 依赖仍待准备，不能报告硬编已经通过。

## Linux 添加设备失败的诊断

用户截图在建立连接阶段显示“连接请求过多，请稍后重试”。服务端 `control/session.rs` 的 `accept_code_lookup()` 和 `get_device_network()` 均按一条控制连接累计最多 20 个不同目标，集合没有时间窗口，连接存活期间不会自动恢复额度。设备列表状态查询与手动添加共享设备码查询额度。本机历史设备超过 20 项，因此该机制可能阻止新增 Linux 设备，并且“稍后重试”文案不能准确说明恢复条件。

独立的新 MCP 连接能解析 Linux 设备码，随后到达“device password has not been entered”，没有复现 RateLimited；虚拟机 Executor 运行正常，日志包含成功的控制服务认证。以上证据指向原 Desktop 控制连接的配额状态，而不是虚拟机服务崩溃。尚未从原 Desktop 连接读取其服务端集合，故保留这一诊断边界。没有重置密码、复制其他服务的凭据、清理历史设备或重启已安装应用，也没有修改服务端限额规则。
